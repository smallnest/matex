# Architecture Smell Report

**Project:** matex (github.com/smallnest/matex)
**Scope:** 全项目（21 个源码文件 + 6 个测试文件，约 3200 行手写 Go，不含生成物）
**Date:** 2026-09-30 17:31
**Analyzer:** smell skill

---

## Executive Summary

matex 是一个刻意走"大道至简"路线的分层脚手架：`cmd/` → `internal/app/`（verticle 装配层）→ `internal/domain/`（业务域）→ `pkg/core/`（基础设施薄封装）。依赖图验证为**单向无环**（`pkg/core` 不反向引用 `internal/`），分层边界干净——`internal/` 无一处直连 pgx/go-redis/franz-go/gomemcache（与 depguard 声明一致），HTTP 边界（`httpx.HandlerFunc` 返回 `(any, error)`）与数据边界（DAO + 泛型扫描）职责清晰。架构层面没有 Critical 问题。

确认的问题集中在两处：**(1) pkg/core 部分包的零值兜底与 tag 默认值双写**，构成 DRY 违规——同一份默认值知识（`16`、`250ms`、`20`、`3s`）需要在 tag 和 `Open()` 两处同步维护，db 包曾因此出过真实 bug（dbtest 直接构造 `db.Config{DSN: dsn}` 时 `ConnectTimeout` 零值导致 ping 立即超时）；**(2) pkg/core 零测试覆盖的包**（db / kafka / redis / memcache / verticle / app 六个包，恰是框架核心），其中 `Run` 函数 112 行承担启动序列全部职责。

另有三处已确认的死代码/未用导出（`statusWriter.hijacked`、`httpx.ErrNoBody`、`kafka.Config.Consume`、`memcache.New`）与两个待测量的复杂度候选。总体健康度：🟢 良好（对 3200 行的脚手架而言），问题均为局部 Warning/Suggestion 级别。

## Architectural Style Detected

**分层架构（Layered）+ 组合根（Composition Root）**，四个物理层：

```
cmd/          → 入口（薄）
internal/app/ → 组合根：verticle.Service 实现，装配 domain
internal/domain/ → 业务域（handler/service/dao）
pkg/core/     → 基础设施（config/db/redis/memcache/kafka/httpx/obs/errs/verticle/app）
```

`pkg/core/verticle` 是"框架驱动层"：`Run()` 统一驱动配置加载 → 基础设施初始化 → Setup → 路由 → 运行 → 优雅退出。这是一套 verticle 生命周期抽象的简化版。

### Style Expectations vs. Reality

| Expectation | Reality | Status |
|-------------|---------|--------|
| 层间依赖单向（外→内） | `go list -deps` 验证无反向引用、无循环 | ✅ |
| 业务不碰驱动库 | internal/ 零直连（grep 验证 + depguard 声明） | ✅ |
| 组合根集中装配 | `internal/app/service.go` 是唯一装配点，显式 Deps 注入 | ✅ |
| HTTP 边界薄（不碰 writer） | HandlerFunc 统一签名，统一信封渲染 | ✅ |
| pkg/core 自身可测 | db/kafka/redis/memcache/verticle/app 六包零覆盖 | ⚠️ |
| 配置默认值单一来源 | tag 与 Open() 双写（db/redis） | ⚠️ |
| 无死代码 | 4 处未用导出/字段 | 🔵 |

### Candidates Requiring Measurement

- **C1 复杂度候选：`config.parseRaw` 的 `lowerKeys` 递归整树拷贝**——每次配置加载对整棵 YAML 树做一次全量 map 拷贝。启动路径冷路径 + 配置热更是低频事件（人手改文件），静态看是 O(n) 额外分配，**实际影响极可能为零**。不成立为 finding。何时升级：若未来引入配置中心高频推送（每秒多次 reload），重测分配。
- **C2 复杂度候选：`httpx.wrap` 每请求 goroutine + channel**——每请求起一个 goroutine 跑 handler、经 channel 传回结果以实现超时切断。相比 `context.WithTimeout` 透传（标准做法，无额外 goroutine），多一次调度与分配。**何时测量**：路由打满基准（wrk 100 并发对比去掉 goroutine 的版本）后再决定；当前无任何性能诉求声明，按 Measure First 降级为候选。

## Detailed Findings

### Finding #1: 默认值双写（tag 与 Open 兜底）

- **Category:** Code / Design
- **Severity:** 🟡 Warning
- **Anti-Pattern:** Duplicated Knowledge（DRY 违规）
- **Location:** `pkg/core/db/db.go:50-55` + `db.go:Open()`（`maxConns`/`connectTimeout`/`slowThreshold` 兜底）；`pkg/core/redis/redis.go:23-27` + `redis.go:Open()`（`poolSize` 兜底）
- **Confidence:** High
- **Evidence strength:** Observed（曾引发真实 bug）
- **Failure or change scenario:** 修改"默认连接数 16"需要同时改 tag 和 Open 内兜底两处；漏改任一处则直接构造 `Config`（测试、工具，如 `cmd/migrate`、`dbtest`）与走 YAML 加载的路径行为分叉。**这已在项目中真实发生**：`dbtest` 直接构造 `db.Config{DSN: dsn}` 时 `ConnectTimeout` 为零值，`Open` 未兜底导致 ping ctx 立即超时、测试失败（后补的兜底是打补丁而非消除双写）。
- **Primary principle:** DRY
- **Description:** 同一份默认值知识存在两处：struct tag（供 config 引擎在 YAML 缺 key 时填充）与 `Open()` 内的 `<= 0` 守卫（供直接构造 Config 的调用方）。tag 是声明式的，绕过 config 引擎的调用方享受不到。
- **Evidence:** `default:"16"` 与 `if maxConns <= 0 { maxConns = 16 }` 并存；redis 同型（`default:"20"` vs `poolSize` 兜底）。
- **Measured/observed impact:** 已发生一次测试故障；每处默认值变更的认知成本 ×2。
- **Recommendation:** 最小修复——`Open()` 兜底保留但**改为单一来源**：兜底值抽为包级命名常量（`const defaultMaxConns = 16`），tag 写不进常量则加注释互指（`default:"16" // keep in sync with defaultMaxConns`）；或提供 `DefaultConfig()` 构造器让直接构造方使用，Open 内兜底仅防御 `DefaultConfig` 之外的畸形值。
- **Verification:** `go test ./...`（dbtest 路径覆盖直构造场景）+ grep 确认字面量只出现在常量定义处。

### Finding #2: pkg/core 框架核心六包零测试覆盖

- **Category:** Testing
- **Severity:** 🟡 Warning
- **Anti-Pattern:** No Tests（框架核心无守护）
- **Location:** `pkg/core/db`、`pkg/core/kafka`、`pkg/core/redis`、`pkg/core/memcache`、`pkg/core/verticle`、`pkg/core/app`（六包 0 覆盖；有覆盖的：httpx 81.1%、errs 67.6%、config 60.2%、helloworld 41.5%）
- **Confidence:** High
- **Evidence strength:** Observed（`go test -cover` 实测）
- **Failure or change scenario:** pkg/core 是所有业务的地基，且是"业务禁直连驱动库"的唯一 choke point——`db.Open` 的 pgxpool 参数拼装、`redis.TryLock` 的 Lua 释放脚本、`kafka.RunConsumer` 的 detached-context 提交、`verticle.Run` 的启动序列，任何一处回归都直接打到所有业务；这些恰是无测试的部分。业务域反而有测试。
- **Primary principle:** 无（测试缺失本身即问题）；Related: Fail Fast（框架 bug 应在框架层测试暴露，而非业务层）
- **Description:** 测试投资倒挂：边缘（httpx/errs）覆盖好，核心（db/kafka/redis/verticle）为零。部分原因是这些包看似需要真实中间件——但项目已有 dbtest/redistest 基座，`db` 包完全可测；`redis.TryLock` 用 redistest 可测；`kafka` 可引入进程内 broker 做集成测试。
- **Evidence:** 覆盖率表（见上）；`redistest`/`dbtest` 存在但只被业务测试消费。
- **Measured/observed impact:** 六包约 1300 行核心代码无回归防护；修改 `db.go`（如最近的兜底修复）只能靠下游测试间接暴露。
- **Recommendation:** 优先级排序：(1) `db` 包（QueryOne/QueryAll/WithTx/migrate，用 dbtest，收益最大）；(2) `redis`（GetJSON/SetJSON/TryLock 语义，redistest）；(3) `kafka.RunConsumer` 提交语义（抽象 commit 决策做纯逻辑测试，或引入进程内 broker）；(4) `verticle.Run`（最小化：WithConf 解析 + fail-fast 路径，可用临时配置文件 + `WithoutConfigWatch`）。memcache 无进程内替身，可最后处理或标注接受。
- **Verification:** `go test -cover ./pkg/core/...` 各包 > 60%。

### Finding #3: `verticle.Run` 112 行六个职责

- **Category:** Design / Cohesion
- **Severity:** 🟡 Warning
- **Anti-Pattern:** Long Method + Divergent Change（六个独立变化方向）
- **Location:** `pkg/core/verticle/verticle.go:Run()`（112 行）
- **Confidence:** Medium
- **Evidence strength:** Observed
- **Failure or change scenario:** 加一种基础设施（如 mongo）、改启动顺序、改配置来源、改 watch 行为——四个互不相关的变化都会编辑同一个函数体。函数当前尚可读（注释分 Step），但每加一个 Step 就更难一眼验证顺序。
- **Primary principle:** SRP
- **Related principles:** KISS（此处不建议过度拆分——见 Recommendation）
- **Description:** Run 顺序混合：配置加载/解析、日志初始化、基础设施初始化 ×4、服务 Setup、HTTP server 构建、closer 编排、配置 watch。112 行、六个职责。
- **Evidence:** Step 注释（Step1-7）本身就是职责清单；每步的失败路径都 `fmt.Errorf("verticle: init X")` 同型。
- **Measured/observed impact:** 变更影响面集中；新增基础设施需理解整函数。
- **Recommendation:** 最小拆分（不过度）：抽 `initInfra(ctx, fc) (*Env, error)`（吸收 db/redis/memcache/kafka 四段 if 块 + closer 收集，Run 少约 40 行）、抽 `buildHTTP(fc, env, svc)`。**不建议**把每个 Step 做成接口钩子链（Over-Abstraction，项目尚无第二个 verticle 复用场景，YAGNI）。
- **Verification:** 重构后 `go build` + 手动冒烟（`make run-min` + curl /healthz）+ 行为不变的代码 review。

### Finding #4: 死代码 / 未用导出（4 处）

- **Category:** Code
- **Severity:** 🔵 Suggestion
- **Anti-Pattern:** Dead Code / Speculative Generality（部分）
- **Location & 明细:**
  | 位置 | 内容 | 性质 |
  |---|---|---|
  | `pkg/core/httpx/server.go:224` | `statusWriter.hijacked` 字段 | Dead Code：写入点为零（grep 验证仅声明处） |
  | `pkg/core/httpx/server.go:257` | `var ErrNoBody error` | Dead Code：零使用点，注释宣称的语义（400）也从未接线 |
  | `pkg/core/kafka/kafka.go:19` | `Config.Consume bool`（含注释提到 demo 注册消费块） | 未用导出：仅 `internal/app/service.go:47` 读取（demo 用 `DemoConfig.Consume`，读的是**服务段**的另一个 Consume）——框架段的这个字段零读取点 |
  | `pkg/core/memcache/memcache.go` | `New()` 构造器 | 未用导出：全仓零调用（文档注释说"used by tests"，但测试从未用它） |
- **Confidence:** High（四项均 grep 全仓验证零使用/零读取）
- **Evidence strength:** Observed
- **Failure or change scenario:** 阅读成本与误导：`ErrNoBody` 让人以为 ReadJSON 会返回它；`kafka.Config.Consume` 与 `DemoConfig.Consume` 同名不同义，配置文档（config.yaml 注释 `consume: false # true 时启动示例消费者`）指向的是哪一个存在歧义。
- **Primary principle:** YAGNI
- **Description:** 框架公开面大于实际使用面。
- **Recommendation:** 删 `hijacked` 与 `ErrNoBody`（保留 `Flush`，SSE 需要）；删 `kafka.Config.Consume`（demo 的消费者开关已在 `DemoConfig`，框架不该知道"示例消费者"）；`memcache.New` 二选一——要么删，要么真给 memcache 写个用它的测试（与 Finding #2 联动）。
- **Verification:** 删除后 `go build ./... && go vet ./... && go test ./...` 全绿。

### Finding #5: `httpx.HandlerFunc` 与 `http.HandlerFunc` 命名冲突

- **Category:** Naming
- **Severity:** 🔵 Suggestion
- **Anti-Pattern:** Vague/易混命名（同包内两种 HandlerFunc 并存）
- **Location:** `pkg/core/httpx/server.go:46`（`type HandlerFunc func(ctx, *http.Request) (any, error)`）与 `server.go:98`（`HandleFunc(pattern, h http.HandlerFunc)`）
- **Confidence:** Medium
- **Evidence strength:** Observed
- **Failure or change scenario:** 用户在同文件混用两种注册方式时，`s.Handle("GET", "/x", h)` 与 `s.HandleFunc("/x", h)` 的 `h` 类型不同但名字都叫"HandlerFunc"，编译错误信息（`cannot use h (variable of type http.HandlerFunc) as HandlerFunc value`）读起来像绕口令。
- **Primary principle:** KISS（认知成本）
- **Description:** matex 的核心类型与标准库类型仅差一个点号，且二者在同一包共存。
- **Recommendation:** 三个选项按侵入度递增：(a) 仅文档强化（包注释已说明"escape hatch"，成本零）；(b) `HandleFunc` 改名 `HandleRaw`，消除同包 `HandleFunc(... http.HandlerFunc)` 的自指混淆；(c) 重命名核心类型为 `Handler`（但会波及全部 skill 文档与已验证代码，**不建议**现在做）。推荐 (b)。
- **Verification:** 改名后 `go build` + 更新 `.opencode/skills/add-domain/SKILL.md` 中的相应示例。

## Refactoring Roadmap

### Immediate Actions (This Sprint)

1. **删除死代码**（Finding #4）：`statusWriter.hijacked`、`httpx.ErrNoBody`、`kafka.Config.Consume`、`memcache.New`（或为其补测试）。半小时内可完成并全量验证。
2. **消除 `httpx` 同包命名混淆**（Finding #5 选项 b）：`HandleFunc` → `HandleRaw`，同步 skill 文档。
3. **db 包默认值单一来源**（Finding #1 的最小修复）：命名常量 + tag 注释互指，消除字面量双写。

### Short-Term (1-3 Months)

1. **补 db 包测试**（Finding #2 优先级 1）：dbtest 基座已就绪，覆盖 Open 兜底路径（防 ConnectTimeout 类 bug 复发）、QueryOne/QueryAll/QueryScalar、WithTx 回滚、ApplyMigrations 幂等。
2. **补 redis 包测试**（优先级 2）：GetJSON/SetJSON 往返、TryLock 的 token 安全释放（他人锁不可释放）、TTL 过期。
3. **拆分 `verticle.Run`**（Finding #3）：抽 `initInfra` 与 `buildHTTP`，保持无钩子链的朴素形态。

### Long-Term (3-12 Months)

1. **kafka 消费者提交语义的测试保障**（Finding #2 优先级 3）：抽出 commit 决策做纯逻辑测试——`context.WithoutCancel` 的关闭期提交是正确性关键，目前无守护。
2. **覆盖率纳入 CI 门槛**：`go test -cover` 各 core 包 > 60% 后，在 `make ci` 中加 `-cover` 断言，防止回退。
3. **候选 C2 的裁决**：若引入性能诉求，跑 wrap 的 goroutine-per-request 基准对比；无诉求则永久关闭该候选。
