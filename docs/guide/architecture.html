架构总览

两条主线：纵向是 verticle.Run 的启动序列，横向是 cmd → internal → pkg/core 的依赖方向。前者决定服务怎么活起来， 后者决定代码往哪放。

分层与依赖方向

每个目录的职责

路径 职责
cmd/<service>/ 一个二进制一个部署单元；main 只调 verticle.Run。
internal/app/ 实现 verticle.Service，把基础设施句柄装配进 domain。
internal/domain/<name>/ 一个业务域三件套：handler.go（HTTP 边界）、 service.go（业务）、dao.go（数据）。
pkg/core/* 基础设施。业务只准从这里进（depguard 强制），第三方驱动被关在里面。
configs/ 框架段 + 每服务一段，段 key 等于 Service.Name()。
migrations/ 按文件名序执行，只追加不修改已有文件。
examples/<feature>/ 每个能力一个可运行示例，离线可跑、带测试——所以 CI 能验证它们。
skills/ 给 AI 的接入规范，与 AGENTS.md 一起充当"生成器"。

启动序列

verticle.Run 的每一步都是 fail-fast：任何一步返回错误，启动就停在那里， 不会带着半初始化状态开始服务。

优雅退出的顺序

// 顺序（app 包保证）：
// 1. 停止 Block 里注册的后台任务（定时任务、消费者循环）
// 2. 关闭 HTTP server，排空在途请求
// 3. flush 链路追踪的 span
// 4. 逆序执行 AddCloser 注册的清理函数，最后关基础设施连接

env.Block("cron", s.sched.Run)                    // 随 ctx 取消而停
env.AddCloser(func() { flushMetrics() })          // 逆序执行，后注册的先跑

顺序是有理由的：后台任务先停，才不会在 HTTP 排空期间继续产生新工作； 基础设施最后关，才能在排空前把请求真正做完。

请求的生命周期

HTTP 侧的每一层也是显式的。两个中间件槽的区别值得记住： Use 走封套（能返回 errs 短路，不碰 ResponseWriter），UseOuter 在 mux 外层 （能改响应头、覆盖 /healthz 与 HandleRaw）。

一致性契约

四条约定，前两条被 lint 强制，后两条被测试与例子的存在形态保证。

约定 强制方式
业务代码不 import 驱动库 depguard internal-no-drivers / examples-no-drivers
业务代码不 import Web 框架 depguard no-web-frameworks
handler 签名统一 类型系统——srv.Handle 只接受 HandlerFunc
每个能力有可运行的离线示例 + 测试 make ci 会跑 ./examples/...，示例坏了 CI 就红
